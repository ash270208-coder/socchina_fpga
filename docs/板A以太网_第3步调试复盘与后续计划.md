## ★★★ 关键突破（写于复盘之后，晚上接手先读这段）

之前的结论"主动发会锁死协议栈"是**错的**。翻到安路官方 `udp_transmit_test.v`
后发现真相：

**安路官方的"主动发送"，从来不是手写 app-TX 状态机，而是把数据灌进
`udp_loopback` 的收口（`app_rx_*`），让 loopback 那套验证过的握手把数据发出去。**

```verilog
// udp_transmit_test.v:612-637（官方主动发送模式的核心）
udp_data_tpg u1_udp_data_tpg(...);          // 测试数据发生器
udp_loopback #(.DEVICE(DEVICE)) u2_udp_loopback(
    .app_rx_data        (tpg_data),          // ★ 把 TPG 数据当"收到的包"喂进去
    .app_rx_data_valid  (tpg_data_valid),
    .app_rx_data_length (tpg_data_udp_length),
    ...  // loopback 原样"回环"发出去
);
```

**我之前的 `tx_frame_sender` 是唯一一个手写 app-TX 握手的实现，而它恰好把
协议栈卡死了。** 所以正确修法不是"换谁主动发"，而是**照抄官方结构**：
数据发生器 → 灌进 `udp_loopback` → 自动发出。板 A 可以继续主动发图，板 B 不用改。

**已完成的修复（今晚直接编）：**

| 文件 | 改动 |
|---|---|
| `net/image_feeder.v`（**新增**） | 读 `img_fifo`，把一帧拆成 N 个小包，喂给 `udp_loopback.app_rx_*` |
| `net/board_a_net_wrapper.v` | `g_image_sender` 分支：`image_feeder` + `udp_loopback` 取代 `tx_frame_sender` |
| `td_project/camera_to_dsi_display.al` | 登记 `image_feeder.v`（CompileOrder 108） |

> ⚠️ 用户仍要在 TD 图形界面确认 `image_feeder.v` 已在工程里（`.al` 会被无头
> 流程覆盖，交接文档 §8.1 的坑）。

## 0. 一句话现状

**已经证明：只要图像发送器 `tx_frame_sender` 去驱动协议栈的 app-TX 接口，
板子的网口就死（ping 不通、ARP 表空）。只要它不驱动，一切正常。**

但**具体卡在哪一段（协议栈 ARP 状态机 / RGMII TX / 收发 FIFO）还没定位到**，
因为缺一个关键观测：**线上到底有没有板子发出的帧**。这正是今晚要用 Wireshark 补上的。

---

## 1. 已确认的事实（全部实测，可复现）

| # | 实验 | 应用层 | ping | ARP 表 |
|---|---|---|---|---|
| A | 第 2 步 bit（`5271175`，`udp_loopback`，端口 2） | 被动回环 | **4/4 通** | 正常 |
| B | 第 3 步 v2（`tx_frame_sender`） | 主动发图 | 0/4 不通 | 空 |
| C | **对照：`USE_LOOPBACK=1`**（其余全同第 3 步：6666/cnn_ds10/img_fifo/视频线） | 回环 | **4/4 通** | 正常 |
| D | **对照：`USE_NO_APP=1`**（发送器例化但永不驱动 app_tx_*） | 不驱动 | **4/4 通** | 正常，LED1 闪=RX 活着 |
| E | `USE_NO_APP=0`（发送器驱动 app_tx_*）的各种改法 | 主动发图 | **全不通** | 空 |

**实验 E 里试过的所有改法，全部失败：**

| 改法 | 目的 | 结果 |
|---|---|---|
| v1：1ms ack 超时放弃 | 怕占死 TX | ❌ |
| v2：不超时 + 读空冻结 | 对齐 loopback | ❌（LED2=request **常亮**） |
| 整帧就位（NEED_FRAME=27648，FIFO 加深 32768） | 发送时数据够 | ❌ |
| 等 `udp_tx_ready` 再拉 request | 对齐 loopback 握手 | ❌ |
| 3s 上电静默 + 800ms 超时 + 300ms 退避 | 躲 ARP 时序 | ❌ |
| 载荷 1402→512 字节 | 猜协议栈吃不下大包 | ❌ |

### 由此确定的铁结论

1. **图像通路无罪**：`cnn_ds10` / `pixel_to_bytes` / `img_fifo` / 视频取数线 /
   加深的 FIFO，在实验 C、D 里全部照样在跑，ping 照样通。
2. **RGMII / 引脚 / 约束 / 时序无罪**：布线后 SWNS +0.39、违例 0、slice 86%、ERAM 69。
3. **唯一的变量 = 发送器驱动 `app_tx_request / app_tx_data_valid / app_tx_data`。**
   它不驱动（D）就通，驱动（E）就死。

## 2. 最可能的根因（仍是推断，但收敛得很窄了）

实验 E 里 **`arp_request_no_reply_error`（LED4）一直是亮的**。这个信号的意思是：

> 协议栈**主动发起了 ARP 解析**（为了把图像发往 192.168.240.2），
> 重试 3 次（`ARP_REQUEST_NUM=3`，间隔 `0x0ffffff` 拍 ≈ 134ms，总共 ~400ms）没收到回应。

这带来一个极其重要的分叉，**Wireshark 一次就能判定**：

| 子假设 | 线上的现象 | 含义 |
|---|---|---|
| **H1**：协议栈「以为」发了 ARP，但实际**没发到线上** | 抓包里**看不到**板子发的「who has .2」广播 | app-TX 活动把协议栈→MAC 的 TX 通路堵死了 |
| **H2**：板子发了 ARP，PC 回了，但**板子 RX 被自己的 TX 活动卡住、没处理应答** | 能看到板子问 .2、也能看到 PC 答 .2，但板子**不答 PC 的 who-has-.1** | 协议栈 RX 侧被 TX 活动占用 |
| **H3**：板子发了 ARP，但 PC 根本没回（PC 侧丢广播） | 板子问 .2、PC 无应答 | 查 PC 防火墙/NIC |

**为什么"主动发"是嫌疑最大的点**：

所有**验证过能工作**的实现，全是**被动发**——

| 实现 | 什么时候发 | ARP 缓存状态 |
|---|---|---|
| 官方 `udp_loopback`（第 2 步通过） | 收到包之后 | 已从收到的包学到对端 MAC，**无需 ARP** |
| 板 B `result_sender.v`（上板通过） | 收到图、CNN 算完之后 | 同上 |
| **我的图像发送器** | **开机定时主动发** | **缓存空 → 必须主动 ARP** ← 唯一没验证过的路径 |

**结论（推断）：这个加密协议栈的 app-TX 接口和它的主动 ARP 解析，可能不能同时工作
——应用层一旦主动申请发送、触发 ARP，协议栈就把自己锁死。** 三条子假设 H1/H2/H3
都能解释所有实测，抓包即可二选一/三选一。

## 4. 今晚的行动计划（按顺序）

> ⚠️ **本节 ②③ 的"rx_seen 被动化 / 板B主动请求"已被顶部「关键突破」取代。**
> 新方案 = `image_feeder` + `udp_loopback`（照抄官方 `udp_transmit_test.v`），
> 已经实现。今晚先按 ① 抓包确认，再直接编新方案，不必再走 ②③ 的旧路。

### ① 【最先做，零成本】Wireshark 抓包（用现在这块 bit，PKT_PAY=512）

**抓包要在给板子上电之前就开始**：

1. Wireshark → 选「以太网」→ **开始抓包**
2. 板子断电再上电（3 秒静默期）
3. 等 8 秒 → `ping 192.168.240.1` → 等 3 秒 → 停止
4. 过滤 `arp or icmp or udp`

**要回答的 4 个问题**（板子 MAC = `02:00:00:00:24:01`，PC MAC = `c4:c6:e6:22:d1:66`）：

| # | 问题 |
|---|---|
| 1 | 板子（源 MAC 02:00:...:01）发了**任何**帧吗？ |
| 2 | 板子发了 ARP「who has 192.168.240.2」吗？ |
| 3 | PC 发了「who has 192.168.240.1」吗？板子回 ARP 应答了吗？ |
| 4 | 板子问 .2 之后，PC 回了「.2 is at c4:c6:...」吗？ |

**判读**（对应 §2 的 H1/H2/H3）：
- 板子一个帧都没有 → H1（TX 被 app 活动堵死）
- 板子问 .2、PC 答了 .2、但板子不答 PC 的 .1 → H2（RX 被占）
- 板子问 .2、PC 没答 → H3（PC 侧）

### ② 【很可能就是最终修法】改成「收到过帧才发」——被动化

无论 H1/H2/H3 哪个成立，修法方向都一致：**板 A 绝不在 ARP 缓存为空时主动发。**

最小改动：给发送器加一个 `rx_seen` 锁存，**收到过至少一个帧之后**才允许发送：

```verilog
// 收到任何帧（ARP/ICMP/UDP 都算）就置 1
reg rx_seen;
always @(posedge udp_clk)
    if (reset)                 rx_seen <= 1'b0;
    else if (temac_rx_valid)   rx_seen <= 1'b1;

// S_IDLE 里把启动条件从  frame_start && armed
//                        改成  frame_start && armed && rx_seen
```

原理：你 ping 板子时，板子**先收到 PC 的 ARP 请求**（广播），ARP 协议天然让板子
**学到 .2 的 MAC**（请求的源 IP 就是 .2）。此时 `rx_seen` 置 1，发送器才第一次出手，
而 ARP 缓存已经满了 → **不再触发主动 ARP** → 不会再锁死。

判读：
- 这版如果 **ping 通 + 图也发得出去** → 根因坐实 =「缓存空时主动发」。单板（PC 当板 B）
  图像通路就此打通，用 `tools\boardA_recv_frame.py` 收图。
- 如果 ping 通但图没发 / ping 又不通 → 再抓一次包，回来我继续切。

### ③ 双板联调要做的协议调整（如果 ② 成立）

最终系统里，板 B 是"收到图才回结果"，而板 A 现在是"收到包才发图"——
**两边都等对方先开口 = 死锁**。所以必须让**板 B 先发**：

- 板 B 周期性发一个小请求包（如 4 字节 `REQ + 帧号`）给板 A
- 板 A 收到请求才发一帧图像

这是被动化后的必然结果，等 ② 验证通过再动板 B 工程。

## 6. 千万别再犯（硬纪律）

1. **先抓包，再 build。** 抓包 2 分钟能回答的，绝不用 15 分钟 build 去猜。
2. **单变量二分。** 每次只改一个东西，用 `USE_NO_APP` / `USE_LOOPBACK` 这类开关切。
3. **LED 映射冻结**，每次实验记表（ping / arp -a / LED1..4 / 时间点）。
4. **改 Verilog 只用编辑工具**，绝不用 PowerShell 的 `Set-Content` / `Out-File`（会加 BOM、毁中文）。
5. **协议栈是加密黑盒**，不要凭"合理推测"下结论——每个结论都要能被线上抓包或对照实验证伪。
6. **app-TX 别手写**：官方 `udp_transmit_test.v` 证明正确姿势是把数据喂给 `udp_loopback`，
   让它那套验证过的握手来发。手写 app-TX 状态机（`tx_frame_sender`）已被实测卡死。
