## 2. 三个必须先说的坑（都踩过）

### 坑 1：指导文档 §7.6 的 `tx_frame_sender` 是错的

`udp_ip_protocol_stack` 的应用侧 TX 是「request → 等 ack → 连续喂数据」。
**第一个字节必须与 `tx_valid` 同一拍就绪**，否则第一个字节会取到上一包的残留，
整包错位一格、长度也差一字节。

指导文档那段 `S_REQ` 里只拉 `tx_valid` 没有装首字节 → **照抄必错**。
板上验证过的 `cnn_boardB/src/net/result_sender.v:179` 写得很清楚：

```verilog
if (tx_ack) begin
    tx_valid <= 1'b1;
    tx_data  <= 8'hAA;   // 第一字节与 tx_valid 同拍就绪   ← 注释就是踩过坑留下的
```

本工程的 `tx_frame_sender.v` 按这个写法重写，并逐拍推演了与 show-ahead FIFO 的配合：

- 载荷字节号 m（0 基）：m=0 是 seq_hi，m=1 是 seq_lo，m≥2 是 `img[m-2]`
- 状态机里 `idx` 与采样拍的对应是 **采样到字节 m 的那一拍 idx = m+1**
- `idx==1` 那拍装载 seq_lo；`idx>=2` 那拍装载 `fifo_q` 并同时拉高 `fifo_rd`
- show-ahead 模式下 FIFO 读地址会预加 1（`ram_fifo.v:246`），所以下一拍 `fifo_q`
  正好是下一个图像字节 ✓
- `fifo_rd` 拉高次数 = `pay-2` = 每包图像字节数，一帧合计 27 648 ✓

### 坑 2：`video_to_axis.v` 根本不需要

指导文档 §7.3 用 `de/vs` 生成 `tvalid/tuser/tlast`。但实际读代码后发现：
**`vpp_top` 本身就是 `tvalid/tuser/tlast` 流**（ISP/DDR 那条链路全是），
`mux_tvalid/tuser/tlast` 与 `raw_rgb_d[21]` 严格同拍。
所以只要给 `vpp_top` 加 4 个输出口即可，**少一个模块**。

### 坑 3：`.al` 绝对不能手改（实施计划 §1 的铁律，实测验证）

TD 在无头流程**结束时**会按它自己的文件表**重写** `.al`。我手工加的 3 个条目
跑完一次就被丢掉，第二次跑全是 `HDL-7144 unknown module` / `HDL-8007 black box`。

- **验证用**：每次跑前把 3 个条目补回去（本记录的脚本就是这么做的）
- **正式构建**：**必须由人在 TD 图形界面里登记**这 3 个文件：
  `net/pixel_to_bytes.v`、`net/tx_frame_sender.v`、`cnn/cnn_ds10.v`

## 3. 核心工作：`cnn_ds10` 为什么装不下，以及怎么改

### 3.1 v1 实测：装不下

v1 是"2 bank × 128 块 × 3 通道 × 15 位 = **11 520 个触发器**"的寄存器堆。
综合后逐实例报告：

```
| u_cnn_ds10 | cnn_ds10 | 9206 (lut) | 45 (ripple) | 11619 (seq) | ... | 1 (dsp) |
```

全芯片被顶到 `#slice* 26 148 / 21 216 = 123.3%`，而第 2 步只剩 **4 899** 个余量。

**注意计划 §7.1 说的"cnn_ds10 实测消耗 3 369"是隔离综合的数字，严重低估**
（和除法器那次一样：隔离值 2 162 → 实际 232/329，方向相反但同样不可信）。

### 3.2 关键诊断：瓶颈是 LUT，不是触发器

`report_area` 的明细说明了问题在哪：

```
#slice*        26 148 / 21 216  (123.25%)
  #used ram     2 704
  #used logic  23 444
    #with luts* 20 057   ← LUT 占掉 20 057 个 slice
    #with adder  2 273
    #reg only*   1 114   ← 纯寄存器只占 1 114 个
```

**所以"只把触发器搬进 ERAM"是不够的** —— 真正的大头是 **256 深寄存器堆的
写译码 + 读 mux**（128 块 × 2 bank × 3 通道的选址），它们几乎 1:1 变成 slice。
必须把"寄存器堆选址"一起消掉，而 ERAM 的地址就是一个计数器。

### 3.3 一个被证伪的假设（记下来别重复）

我一度以为"条纹末 `for` 循环清整个 bank"是元凶（11 520 个清零 mux）。
改成"每块在条纹第一个像素直接装载"后——**LUT 一个都没省**（36 930 → 36 926）。
原因：安逻辑的触发器**自带同步复位端**，清零 mux 是免费的。
所以这条路本身没错（少了一次清 bank 的遍历，且累加器不再需要复位端），
但**它不是瓶颈**。

### 3.4 v2 架构：把 10×10 拆成"先横后纵"

```
a) 横向段和（寄存器，~45 FF）
   块内 10 个像素：bx==0 装载，其后相加 -> blk_r/g/b = 该块这一行的 10 像素和

b) 纵向累加（3 个 ram_2port = 256x20 真双口 ERAM）
   地址 = {bank, ox[6:0]}：bit7 选 bank，低 7 位是块列号
   **端口 A**：dia = doa + blk，每个块末写一次
   ram_2port 是 REGMODE="NOREG" -> 读是组合的 -> 读-改-写**同拍完成，无需状态机**

c) 初始化：条纹**第 0 行装载**（by==0 时 dia = blk，不累加）
   等效"清零后再累加" -> 不需要清 bank 通路，也不需要考虑上电清零

d) 排空：条纹末切 bank 后用**端口 B** 读刚完成那个 bank 的 128 个块和，
   一个乘法器分 3 拍算 R/G/B 的 ÷100（4 拍 1 个块，与 v1 输出节奏完全一致）
   端口 A/B 地址不同（一个 {bank,ox} 一个 {~bank,ox}），**天然无冲突**
```

精度不变：÷100 仍用定点 `(x*10486 + 2^19) >>> 20`，误差 ≤0.006 LSB。

### 3.5 `#dsp` 超标的修法

v1 的 `avg()` 在同一拍被调用 3 次 → 3 个 DSP → `#dsp 41 / 40 = 102.5% ❌`。
改成 `m_in`/`m_out` **一个乘法器分时复用**（排空节奏本来就是 4 拍/块，够用）
→ `#dsp 39 / 40` ✅。

## 4. 验证

### 4.1 功能等价性：ModelSim 独立参考模型

`sim/tb_cnn_ds10.v` 把整帧 1280×720 存下来，在 DUT 每输出一个块时，
**独立地从帧缓存重算 10×10 块和**再用同一个定点式 ÷100 逐位比较
（不是镜像 DUT 的累加过程，所以能查出累加/装载的逻辑错误）。

```
输出块数 : 9216  (期望 9216)
tuser 数 : 1     (期望 1)
tlast 数 : 72    (期望 72)
数据错误 : 0
 >>> PASS
```

**两份 ERAM 行为模型故意不初始化（保持 X）**，用来证明"第 0 行装载"确实生效、
没有任何"先读后写"。v1 和 v2 都跑通了这个 tb。

### 4.2 综合（门级 / report_area）

见 §0 表格。`u_cnn_ds10 = 136 LUT + 105 ripple + 114 seq + 3 ERAM + 1 DSP`。

### 4.3 端口与协议

| 项 | 值 |
|---|---|
| 板 A IP / MAC / 本地端口 | `192.168.240.1` / `02:00:00:00:24:01` / `1`（未变） |
| **目的 IP / 端口** | `192.168.240.2` / **`6666`**（原 `2`，低位端口在 PC 上被占过，已换掉） |
| 包结构 | `[seq_hi, seq_lo]` + 图像字节，大端序号 0..19 |
| 包长 | 包 0~18：2+1400 = 1402；包 19：2+1048 = 1050；合计 27 648 = 128×72×3 ✓ |
| 字节序 | 逐像素 R,G,B（由 `pixel_to_bytes` 保证） |
| 帧率 | 每 6 帧发 1 帧（≈10 fps） |

### 4.4 电脑端验收脚本

`tools/boardA_recv_frame.py`（纯标准库，不用装 numpy/Pillow）：

```powershell
# PC 网卡先设成 192.168.240.2 / 255.255.255.0
python tools\boardA_recv_frame.py --count 5 --scale 8
# 输出 frame_001.png ... frame_005.png（128x72，放大 8 倍便于肉眼比对）
# 并打印每帧 RGB 均值，可与 HDMI 上的画面比对色调
```

脚本会校验每包序号与长度，不符就丢弃并报出来 —— 所以它同时也是协议检查器。
