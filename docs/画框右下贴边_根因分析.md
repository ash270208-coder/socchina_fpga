# 画框「下边贴底、右边贴右、框很大、脸不在框正中」根因分析

> 2026-10-25 ｜ 板 A：`lab_ex1_mipi_hdmi+vpp` ｜ 涉及文件：`osd_box_drawer.v`、`design_top_wrapper.v`、
> `board_a_net_wrapper.v`、`net/rx_result_parser.v`；板 B：`cnn_head_dec.v`、`cnn_top.v`
>
> 结论先说：**板 A 的画框数学是对的，错的是"裁剪策略"**。
> 板 B 给的框本来就是"以中心回归"的，而且**尺寸偏大**（现在最大的锚框 3 = 45.6×49.6 格 = 456×496 px，
> 占画面高度 69%）。板 A 原来只把**右下角**夹到 1280/720、左上角原样不动 —— 于是任何"框比剩余画面大"
> 的情况都被画成**从脸的左上角一直拉到屏幕角**：框看起来巨大、右下贴边，而可见矩形的中心被推向左上，
> 所以脸看起来偏在框的左上角。

---

## 1. 5 秒自检：读右上角的 X/Y/W/H

`osd_box_drawer` 的读数是**屏幕上实际画出来的框**（`READOUT_RAW_CELLS = 0`）。
如果出现下面任意一条，就 100% 是被裁剪，而不是"板 B 报了个巨大的框"：

| 读数特征 | 含义 |
|---|---|
| `H == 720 - Y` | 下边被夹在 719（贴底） |
| `W == 1280 - X` | 右边被夹在 1279（贴右） |
| `X`、`Y` 跟随脸，`W`/`H` 随位置变化而变化 | 同上（W/H 不是检测值，是 1280-X / 720-Y） |

把 `READOUT_RAW_CELLS` 改成 `1` 就能对照看板 B **原始报的**格坐标（不裁剪），
两者一比即可看出被裁掉了多少。

## 2. 证据链（板 A 侧，逐行）

### 2.1 几何链本身是对的

```
板 B：x1, y1, w, h        (128×72 检测格, 8 bit)
  → board_a_net_wrapper.v   O_face_x/y/w/h = rx_result_parser 的 x1/y1/w/h（原样，不做运算）
  → design_top_wrapper.v    face_x/y/w/h_final = S_face_x/y/w/h（原样）
  → osd_box_drawer.v        scaled_* = I_face_* × SCALE_FACTOR(10)
                            box_x1 = scaled_x,  box_x2 = min(scaled_x+scaled_w, 1280)
                            box_y1 = scaled_y,  box_y2 = min(scaled_y+scaled_h, 720)
```

1280/128 = 720/72 = 10，所以 `×10` 是对的；`rx_result_parser` 的字节序（`[2]=valid [3]=x1
[4]=y1 [5]=w [6]=h`）与板 B `result_sender.v` 一致；板 B 回包的 `w/h` 也确实是"宽/高"
（`cnn_head_dec.v` 里 `wi/hi` 由 `anchorW·exp(tw)` 得到，不是右下角坐标）。
**所以不存在"坐标换算错、宽高被翻倍"这类问题。**

### 2.2 问题在 `osd_box_drawer.v` 的裁剪

```verilog
// 旧代码（第 108~113 行）
wire [12:0] clipped_x1 = (scaled_x >= SCREEN_W) ? SCREEN_W : {1'b0, scaled_x};
wire [12:0] clipped_y1 = (scaled_y >= SCREEN_H) ? SCREEN_H : {1'b0, scaled_y};
wire [12:0] clipped_x2 = (raw_x2 > SCREEN_W) ? SCREEN_W : raw_x2;   // ← 只夹右下
wire [12:0] clipped_y2 = (raw_y2 > SCREEN_H) ? SCREEN_H : raw_y2;   // ← 只夹右下
```

`x1`/`y1` 原样保留 + `x2`/`y2` 夹到边界 ⇒

* `x1 + w >= 128 格` → 右边**必然**落在 1279
* `y1 + h >= 72 格`  → 下边**必然**落在 719

而板 B 的框是"中心回归"的（`x1 = cx - w/2`），只裁右下不动左上，可见矩形的心就被推向左上，
脸因此看起来**偏在框的左上角**（偏移量正好是"被裁掉的一半"）。

### 2.3 仿真实测（`work_boxdiag/tb_box_raster.v`，真实 1280×720 光栅）

## 3. 为什么 10-23 之前只是"下边贴底"，现在连"右边贴右"也来了

板 B 在 2026-10-24 晚换了重训后的模型（当前 RTL 的锚框常量 = `retrain_v2/out_v2_v9`）。
**k-means 锚框整体长大了一档，这就是"框突然变得很大"的直接原因**：

| 锚框 | v1（10-24 之前） | v2_v9（现在 RTL 里） | 线性放大 |
|---|---|---|---|
| 1 | 12.78 × 8.48 | 14.00 × 14.53 | ×1.40 |
| 2 | 16.57 × 16.08 | 25.53 × 27.55 | **×1.63** |
| 3 | 37.10 × 29.89 | **45.61 × 49.60** | ×1.44 |

换成屏幕像素，以及"什么时候会贴边"：

| 框尺寸（格 → px） | 下边贴底的条件 | 右边贴右的条件 |
|---|---|---|
| 21 × 23 → 210 × 230（v1 实测常见值） | 脸顶 y ≥ 490 px | 脸左 x ≥ 1070 px |
| 37.1 × 29.9 → 371 × 299（**v1 锚框 3**） | 脸顶 y ≥ 421 px | 脸左 x ≥ 909 px |
| **45.6 × 49.6 → 456 × 496（v2_v9 锚框 3）** | **脸顶 y ≥ 224 px** | **脸左 x ≥ 824 px** |
| 51 × 58 → 510 × 580（实测最大） | 脸顶 y ≥ 140 px | 脸左 x ≥ 770 px |

也就是说：**只要模型选中锚框 3，脸顶低于 224 px 就一定会被画成"下边贴屏幕底"** ——
这在正常坐姿/站姿下几乎是必然，所以表现为"总是"。

另外板 B 的 `cnn_head_dec.v` 只把 `x1/y1` 夹进画面，**没有把 `x1+w` / `y1+h` 夹进画面**：

```verilog
// cnn_head_dec.v 第 98~103 行
wire [7:0] x1i = (x1r < 13'sd0) ? 8'd0 : (x1r > 13'sd128) ? 8'd128 : x1r[7:0];  // 只夹左上角
wire [7:0] y1i = (y1r < 13'sd0) ? 8'd0 : (y1r > 13'sd72)  ? 8'd72  : y1r[7:0];  // 只夹左上角
wire [7:0] wi  = (wiq > 13'sd255) ? 8'd255 : wiq[7:0];                          // 宽高只防溢出
wire [7:0] hi  = (hiq > 13'sd255) ? 8'd255 : hiq[7:0];                          // 宽高只防溢出
```
所以"越界量"会原封不动传到板 A。

## 4. 已做的修改（板 A）

`osd_box_drawer.v` 新增 4 个参数（默认值即新行为，顶层 `design_top_wrapper.v` 里已显式写出）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `FIT_MODE` | `2'd1` | 0 = 旧行为（右下硬裁，仅用于回归对照）<br>1 = **保尺寸 + 围绕框中心 + 整框平移进屏幕** |
| `SHRINK_LOG2` | `2'd0` | 显示侧收缩倍数（围绕中心）：0=×1.0 1=×0.5 2=×0.75 3=×0.875 |
| `MAX_W_CELLS` | `8'd128` | 显示侧最大框宽（128×72 检测格），128 = 不限制 |
| `MAX_H_CELLS` | `8'd72` | 显示侧最大框高，72 = 不限制 |

行为要点：

1. **只要框能完整放进画面，两种模式完全一致**，不会引入任何偏移（回归用例 ①）。
2. 越界时新策略**不再切掉右下角**：尺寸保持板 B 报的值（或按 `MAX_*`/`SHRINK` 收缩后的值），
   整框平移到屏幕内，收缩和平移都**围绕框中心**，所以脸不会跑出框的中心。
3. 新增"左上角整个在画面外"的拒绝条件（`x1 ≥ 128 格` 或 `y1 ≥ 72 格`），
   并先把 `w/h` 夹到屏幕尺寸内，杜绝 8 位 `w/h = 255` 时算出回绕坐标（回归用例 ⑤）。
4. `FIT_MODE = 0` 可以 1 行回退到原行为。

### 怎么用它把"框太大"调下来（不动板 B）

先看读数（`READOUT_RAW_CELLS = 1` 看板 B 原始值）。如果板 B 报的 `w/h` 就明显大于脸：

1. `SHRINK_LOG2 = 2'd3`（×0.875）→ 不够再 `2'd2`（×0.75）→ 最后才 `2'd1`（×0.5）；
2. 或者按绝对尺寸限幅：演示距离固定时，`MAX_W_CELLS = 60 / MAX_H_CELLS = 66`（≈600×660 px）通常够用。

两者都是**围绕框中心**收的，脸不会因此偏向一边。

## 5. 板 B 侧才是"框太大"的根（建议同步改）

板 A 只能保证"框完整可见、脸居中、读数不再出现 W=1280-X"，**框本身的绝对大小由板 B 决定**。
要给一张"贴合脸"的框，按代价从低到高：

1. **把框夹进画面（4 行，改 `cnn_head_dec.v`）**：让 `x1+w ≤ 128`、`y1+h ≤ 72`，
   并且**围绕中心**缩，这样板 A 收到的永远是一个合法的框，也不会再把"越界"传下去。
2. **收小锚框 2/3 并重训**：`out_v2_v9` 的锚框 2 是 25.5×27.5 格（=255×275 px），
   在正常演示距离（脸高约 18~20 格）下大了一倍多。按"脸占画面高度 25%~50%"重做 k-means，
   锚框大致落在 `10×12 / 18×22 / 30×36` 这一档比较合适。
3. 复训时**直接回归"脸框"而不是"锚框+偏移"**（或用 IoU 损失），能显著缓解"大脸给小框、小脸给大框"。

# 附：2026-10-25 上板复测后的追加结论（**重要，改变了定性**）

改完 `FIT_MODE` 后上板，照片读数变成 **`X:0000 Y:0000 W:1280 H:0720`**，
且肉眼看到"上下两条边都贴上下边界，左右两条边在边界和正常宽度之间跳变，H 恒为最大"。

## A. 这条读数说明什么

两行读数是同一个 latch，所以：

| 读数 | 反推 | 结论 |
|---|---|---|
| `H = 0720` | `box_h = 720` | 只有当 `h ≥ 72 格` 时才会被夹成满高 ⇒ **板 B 报的 h ≥ 整幅高度** |
| `Y = 0000` | `fit_y1 = 720 - box_h = 0` | 同上 |
| `W = 1280` / `X = 0000` | `box_w = 1280` | **板 B 报的 w ≥ 128 格**（= 整幅宽度）|
| W 在 1280 和 ~340 之间跳 | w 在"≥128"和"≈34"之间跳 | 板 B 的 w 也不稳定 |

也就是说：**板 B 回包里的框至少和整个 128×72 检测图一样大**，等于"整幅画面"当成人脸框。
板 A 只是忠实把它画出来（`work_boxdiag/tb_box_raster.v` 的探针 P 复现了这张照片：
`0,0,255,255 → 旧策略 (0,0)-(1280,720)`）。

## B. 已排除：板 B 的权重/锚框/定点常数

逐字节比对（部署的 `prj/al_ip/cnn_rom_*/**.dath` vs `matlab/retrain_v2/out_v2_v9/*.mem`）：

```
cnn_rom_w1  w2  w3  w4  wh  exp  b1  b2  b3  b4  bh     → 11/11 全部 MISMATCH=0
src/cnn_params.vh  == out_v2_v9/cnn_params.vh            → 完全一致
cnn_head_dec.v 的 AW1..AH3 == out_v2_v9/params_summary   → 完全一致（Q12 精确）
cnn_top.v 的 5 个 MOUT_Q32 / SCORE_TH_Q12                → 与 v9 一致
```
所以**解码常数不是错因**。剩下两种可能，且只能用数据区分：

1. **模型对实时帧的回归本身就崩了** —— `exp(tw) ≥ 2.8`、`exp(th) ≥ 1.45`（相对锚框 3），
   即检测头的 `tw/th` 被顶到输出饱和区。典型原因是送进网络的图像不在训练分布内
   （对比度/亮度/纵向条纹），或网络某一级输出被搞坏。
2. **板 A 解析到的 w/h 不是板 B 的 w/h**（字节错位/重锁）。

判定方法见 §D。

## C. 这一版做了什么（先把画面救回来，并留下可判定的读数）

`osd_box_drawer.v` 又加了 3 个参数（`design_top_wrapper.v` 已按生产值填好）：

| 参数 | 生产值 | 作用 |
|---|---|---|
| `SANITIZE` | `1` | `h > 1.5w` 时判 h 不可信，按 `1.25w` 重算（即 10-23 文档提的兜底）。人脸 h/w 只可能 1.1~1.5，绝不会 >1.5 |

同时这也修正了附 1 的定性：板 B 的 `w/h` **不是一直饱和**，而是**间歇饱和**
（之前那张 `X:0000 Y:0000 W:1280 H:0720` 抓到的是饱和的那一帧）。
所以剩下的活只有一个：**让板 B 不再吐饱和框**（见 §E）；
在那之前，`SANITIZE` + `MAX_*` 就是兜底，只在异常帧生效。

> 判据：如果框突然变成"几乎占满画面"，立刻看读数 ——
> 若显示 `W:0255 H:0255`（或 `W≥0128` / `H≥0072`），就是板 B 的饱和帧；
> 若显示正常（如 `W:0049 H:0054`）而框很大，才是板 A 的问题。

另外注意：本帧的框 `h=54` 格（540 px）略小于整颗头、基本圈住脸 ——
这是模型"框偏小"的已知问题（`P0_框放大与平滑_板A补丁_20261024.md`），与本次的贴边 bug 无关。
