## 2. 相对《实施计划》§5.2 的三处修正（**这就是本次最重要的经验**）

### 修正① §5.2 那段"最小 UDP 回环"是**错的**，已换成官方 `udp_loopback.v`

§5.2 建议：

```verilog
assign app_tx_data_request = app_rx_data_valid && udp_tx_ready;
assign app_tx_data_valid   = app_rx_data_valid;
assign app_tx_data         = app_rx_data;
assign udp_data_length     = app_rx_data_length;
```

这套组合逻辑**不满足协议栈应用侧的握手**：TX 侧是
`app_tx_request → 等 udp2app_tx_ack → 再连续喂 app_tx_data_valid`，
而 `app_rx_data_valid` 是**逐字节**的流有效。直接把它组合接到 TX 口，
等于不等 ack 就往 TX 灌数据，且 `app_tx_data_length` 在帧头处还不一定有效。

反证在官方模块里：`udp_loopback.v` 的启动条件是
`(udp_packet_fifo_data_cnt > 0) && (~app_rx_data_valid) && udp_tx_ready`
—— **必须先把整包收进 FIFO、等 RX 结束，才能发**。

所以本次用安路 APUG013 官方 `udp_loopback` + `ram_fifo`（`SHOW_AHEAD_EN=1`）。
代价：`ram_fifo` 深度 2¹⁶×8 bit ≈ 26 块 ERAM。第 3 步换上图像通路后这块 FIFO 会整个删掉。

> 这条正好套用《实施计划》§9.6 的纪律：**遇到"别人能用我不能用"，第一步就去对照能用的工程**，
> 不要凭文档推断。

### 修正② LED 位宽：`{ net_led, S_por_arst_n, S_pll_lock }` 是 5 位进 4 位口

§5.3 给的 `assign led = { net_led, S_por_arst_n, S_pll_lock };`
左边 `led` 是 `[3:0]`，右边 3+1+1 = 5 位 —— 位宽不匹配。
本次改成 4 位 `{ net_led[2], net_led[1], S_pll_lock, net_led[0] }`（见 §1.4）。

### 修正③ 工程里**已经有一个** `ph1p_phy_pll_wrapper_25a56e5ce2f9`，不能再复制一份

`user_source/ip_source/PLL/RTL/ph1p_phy_pll_wrapper_25a56e5ce2f9.v` 与 stage1 的副本
**字节完全相同**。如果把 stage1 的副本也加进工程，TD 会报：

```
HDL-7201 CRITICAL-WARNING: overwrite current module
  'ph1p_phy_pll_wrapper_25a56e5ce2f9' in ../user_source/hdl_source/net/...v(2)
```

虽然两份定义一致、功能无损，但**关键警告会淹没真正的问题**。
正确做法：**不要**复制这个 wrapper（视频 PLL 的 IP 已经把它带进工程了，
网络 PLL 的 `pll_gen_1.v` 直接复用同一个模块即可）。

### 5.6 slice 回退的资源账（**全部来自布线后 `phy_1/*.area` 实测**）

#### 5.6.1 先量清楚"缺口到底多大"

```

cnn_ds10 单独综合    +3 369

```

#### 5.6.2 `u_anlogic_logo_rom` 的真实形状（这决定 ERAM 代价）

`user_source/hdl_source/anlogic_logo_rom.v`（298 KB）实测：

| 项 | 实测 |
|---|---|
| 布线后占用 | **1 721 logic lut / 0 ERAM / 4 seq** |
| 结构 | `case(I_addr)`，`input [14:0] I_addr`，`output reg [24:0] O_pixel` |
| **非空条目数** | **6 387**（不是 32 768） |
| 地址范围 | 5 494 ~ 20 426，**跨度 14 933** |
| 数据语义 | 25 bit 中 **bit24 恒为 1**（"不透明"标志），低 24 bit 是 RGB |
| default | `default: O_pixel = 25'd0;` → **空地址全透明**，所以密集 ROM 填 0 **语义完全等价** |

**所以它是一个"稀疏查表"，不是 32 K 深表。**

#### 5.6.3 ERAM 每块可用位数（实测标定）

`u_net/u_loopback/udp_packet_fifo`（`ram_fifo`，`ADDR_WIDTH=16`、8 bit）：
`65 536 × 8 = 524 288 bit` → 实测 **28 块** ⟹ **≈ 18.7 Kbit / 块**。
（`PH1P_LOGIC_ERAM` 用 `.IMPLEMENT("20K")`，标称 20 Kbit，实用约 18.4~20.5 Kbit。）

#### 5.6.4 三种做法的 ERAM 代价

| 做法 | 深度 × 宽度 | 位数 | ERAM 估算 |
|---|---|---|---|
| A 满量程密集 ROM | 32 768 × 25 | 819 200 | **≈ 44 块**（乐观 40） |
| **B 按真实地址跨度**（减基址 5 494 → 16 384 深） | 16 384 × 25 | 409 600 | **≈ 22 块**（乐观 20） |
| C 紧凑包围盒（要重排数据） | 10 240 × 25 | 256 000 | **≈ 14 块** |

> 《实施计划》§7.2 的"≈32 块" = `32 768 × 20 bit ÷ 20 480 = 32.0` —— 它按 **20 bit 宽**算的，
> 而实际数据是 **25 bit 宽**。所以**按满量程做实际要 40~44 块，不是 32**。

#### 5.6.5 ERAM 预算

```
起点（第 2 步布线后）              80 / 108   余 28
第 3 步删掉 udp_loopback                  +28       ← 实测 u_loopback 正好占 28 块
第 3 步新增 img_afifo (8bit×4096)          -2
                                  可用 = 54 块
```

| ROM 做法 | 用掉 | 剩 | 第 3 步后总计 | 判断 |
|---|---|---|---|---|
| A 满量程 | 44 | 10 | **98 / 108 = 90.7 %** | ⚠️ 能装但很紧，估算稍有偏差就爆 |
| **B 按真实跨度** | 22 | 32 | **76 / 108 = 70.4 %** | ✅ 推荐 |
| C 包围盒 | 14 | 40 | **68 / 108 = 63.0 %** | ✅ 最省，但要重排数据 |

**结论：ERAM 够，但前提是别机械地把 `case` 换成满量程 ROM。**

>    netlist 里是 `SubSft[0].i` … `SubSft[47].i` 的 48 级减法移位阵列，`parameter PIPLE = 50`。
>    它不是 DSP 除法器。

> **外层握手已经是 done-based，改动集中在 `awb.v` 一个文件**（只需调 `DIV_LAT` /
> 改成纯 `done_div` 等待）。

> **更正后的推荐顺序**：先做 **③（0 ERAM，只动 `awb.v`）**，它一个就够填 573 的缺口；
> 若想要给第 4 步画框留大余量，再叠加 **①-B（+22 ERAM）**。两者不冲突。

### 5.8 ⚠️ 本次引入的 setup 违例（待解决）

**现象**（2026-10-10 12:05 布线后）：`SWNS −0.075 ns`，**1 个违约端点**，
`HWNS +0.020 ns` 无 hold 问题。上一次（10:53，原 IP）是 `SWNS +0.104 ns`、违例 0。

**违例路径**：

```
组   : net_pll_clk_125m_0 → u_net/u_clk_gen/u_pll_0/pll_inst/u_PH1P_PHY_PLL.clkc[4]
        （temac_clk 0° 125MHz → TXC 90° 125MHz）
起   : u_net/u_trimac/u_tx_clk_en_gen/... (0° 域寄存器)
终   : phy1_rgmii_tx_clk_syn_2.rst        （RGMII TXC 输出 ODDR 的复位脚）
预算 : 2.000 ns（90° 相位关系）   数据路径 1.331 ns（其中 net 1.194 ns = 90%）
Slack: −0.075 ns                  逻辑级数 0（纯 clk2q + 走线）
该组共 3 条路径，仅 1 条违约；hold 余量 +5.373 ns
```

**性质**：`tx_reset = reset_reg2[1]`（`temac_block.v:176`，**由 0° 的 `gtx_clk` 打拍**）
驱动 `tx_clk_en_gen.reset`（6 个寄存器）和 3 个 TX ODDR 的 `.rst`，扇出 11。

**为什么只有 TXC 那个 ODDR 中招**（`rgmii_interface.v`）：

| ODDR | 时钟 | 数据来源 | 预算 |
|---|---|---|---|
| `rgmii_txc_ddr` | **`tx_clk_90`（90°）** | `tx_clk_en_gen`（0° 域） | **2 ns** ← 紧 |
| `rgmii_txd_out[3:0]` | `tx_clk`（0°） | 0° 域 | 8 ns ✓ |
| `ctl_output` | `tx_clk`（0°） | 0° 域 | 8 ns ✓ |

**只有 TXC 的 ODDR 挂在 90° 时钟上**，所以该组总共只有 3 条 0°→90° 路径。
其中两条是 `rgmii_txc_en`/`_shift`（千兆模式下按 `tx_clk_en_gen.v:130-134` 是常量 0/1），
第三条就是 `tx_reset` → 复位脚 —— 而它扇出 11、离 IO 远，实测**走线占 92%（1.36 ns）**。

**重跑一次 P&R 无效**：第二次（12:37）同一条路径反而更差（−0.075 → −0.236 ns），
说明不是布局随机性，是这条路径本身在这个设计里就摆不开。

**修复过程（试了 4 轮，前 3 轮都失败 —— 记录下失败原因，别再重复）**：

| 轮 | 做法 | 结果 | 失败原因（实测） |
|---|---|---|---|
| 1 | 直接重跑 P&R | ❌ | 同一条路径 −0.075 → **−0.236 ns**，不是随机性 |
| 2 | 一个 `tx_reset_io` 打拍后驱动全部 6 个 ODDR 复位脚 | ❌ | 报告显示该 net **扇出 6**、要跨 6 个不同 IO 单元，一颗寄存器没法同时贴近 6 个位置，**走线仍 1.369 ns** |
| 3 | 同时写 `tx_reset_io` + `tx_reset_txc` 两颗**同逻辑**寄存器 | ❌ | **综合器把两颗直接合并成一颗**：`pr.timing` 里那条 net 仍然是 `tx_reset_io`、扇出 6。**手工复制寄存器会被合并掉** |
| 4 | **只留 TXC 一颗扇出=1 的寄存器**（其余 5 个 ODDR 直接接 `tx_reset`）+ `//synthesis keep`；同时加 SDC 兜底 | ✅ | — |

**最终改动（两个文件）**：

**(a) `net/rgmii_interface.v`** —— 只给唯一挂在 90° 时钟上的 TXC 那个 ODDR 单独打一拍：

```verilog
reg tx_reset_txc;   //synthesis keep
always @(posedge tx_clk)        // ⚠ 必须是 0° 的 tx_clk，不能用 tx_clk_90
   tx_reset_txc <= tx_reset;
// 只有 rgmii_txc_ddr 用 .rst(tx_reset_txc)；其余 5 个 ODDR 仍用 .rst(tx_reset)
```

| 路径 | 域 | 预算 | 说明 |
|---|---|---|---|
| `tx_reset` → `tx_reset_txc` | 0°→0° | **8 ns** | 同域，走线随便长 |
| `tx_reset_txc` → `TXC ODDR.rst` | 0°→90° | 2 ns | 但**扇出=1**，布局器能把它紧贴 TXC 的 IO 放 |

> ⚠️ 三条禁忌：① 不能用 `tx_clk_90` 打拍（输入侧会变成 2 ns 跨越）；
> ② 扇出必须保持 1；③ **不要写第二颗同逻辑的寄存器**（会被合并，前功尽弃）。

**(b) `td_project/camera_to_dsi_display.sdc`** —— 兜底，把这条**复位**路径按准静态放宽：

```tcl
set_max_delay 4.000 -datapath_only -to [get_pins {phy1_rgmii_tx_clk_syn_*.rst}]
```

TD 的时序例外报告确认它**已应用**（匹配 1 条路径）：

```

```

> ✅ 用 `set_max_delay` 而不是 `set_false_path`：路径**仍在时序分析范围内**、
> 仍出现在报告里，只是给了一个对"准静态复位"合理的上限。
> ✅ **只放宽这一个复位脚**：同一个时钟组里 `rgmii_txc_en`/`_shift` 的两条数据路径
> （真正决定 RGMII TXC 相位、决定 PHY 采样窗口的）**仍然保持 2 ns 检查**，
> 没有被排除，也没有被藏掉。这正是《A板以太网改造方案.md》§13 风险 6 所要求的纪律。
